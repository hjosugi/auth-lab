JWT / JOSE

A JWT is three base64url segments — header.payload.signature — joined by dots. The signature covers the exact text of the first two segments. Reading it once removes most of the mystery.

Decode any JWT

Sign & verify (HS256, real HMAC)

The alg=none forgery

The classic JWT attack. Press the button: it rewrites the payload to sub=admin and sets alg=none with an empty signature, then loads it into the decoder above.

What the library refuses, and why

  • alg=none — JWS.verify requires an explicit algorithm allow-list with no default; 'none' is never in it.
  • RS256→HS256 confusion — keys are typed, so an RSA public key can never be fed to HMAC as a secret.
  • jwk / jku / x5u headers — refused outright; a token may never nominate its own verification key.
  • Claim validation — iss, aud (must contain us), exp, nbf, iat, and OIDC nonce are all checked, not just the signature.
Source: authlab/jose/jws.py, authlab/jose/jwt.py

OAuth 2.0 + Security BCP & OpenID Connect

OAuth is delegation — letting an app act for you, scoped. OIDC adds authentication on top: the ID token tells the app who you are.

The grants, and which to use

GrantForVerdict
authorization_code + PKCEweb apps, SPAs, mobilethe default for anything with a user
client_credentialsservice-to-servicecorrect for machines (no user)
device_codeTVs, CLIs, no browsercorrect for input-constrained devices
refresh_tokenrenew without re-loginwith rotation + reuse detection
implicit—OAuth 2.1 draft omits it (token in the URL fragment)
password (ROPC)—OAuth 2.1 draft omits it (app sees the password)

ID token vs access token — the confusion that breaks APIs

ID token (OIDC) aud = the CLIENT purpose: "who logged in" consumed by: the app typ: JWT
access token (OAuth) aud = the API purpose: "may call this API" consumed by: the resource server typ: at+jwt
Sending an ID token to an API is a real, common bug. authlab's resource server rejects it on both typ and aud. Try it in the Attacks tab.

PKCE — Proof Key for Code Exchange

PKCE binds the authorization code to whoever started the flow, so a stolen code is useless. This is the single most important OAuth hardening of the last decade.

Generate a verifier / challenge pair

The verifier stays secret on the client. Only its SHA-256 (the challenge) travels through the browser.

Verify a code_verifier against the challenge

This is what the token endpoint does. Paste the verifier back (or change one character to see it fail).

Why plain is not PKCE

The plain method sends the verifier itself through the browser — exactly the channel PKCE assumes is compromised. authlab refuses it and requires S256. And if the server accepted a request with no challenge, an attacker would simply omit it, so PKCE is required for public clients, not optional.

Password storage

Never store the password. Salt per user. Be slow on purpose. Store the parameters so you can raise the cost later.

Hash a password (PBKDF2, real)

The Python library defaults to scrypt (memory-hard); this browser demo uses PBKDF2 because that is what Web Crypto exposes. Same principle: deliberate slowness.

The user-enumeration timing oracle

A naive login returns instantly for an unknown user but slowly for a known one. That gap tells an attacker which usernames exist.

The fix (fake_verify in authlab/passwords/hasher.py) burns the same time for a missing user as for a wrong password.

Trust binding の negative test

WebAuthn は challenge だけでは不十分です。RP は type、challenge、origin、rpIdHash、UP/UV flags、署名をすべて検証します。

本番設計で別途決めること

  • Attestation: none は端末追跡を避けやすい既定。この教材は形式を表示するだけで attestation chain を信頼しません。端末 provenance を要求する管理環境だけ、プライバシーとメタデータ検証を設計して direct を使います。
  • Sync / backup: BE/BS flags は credential が同期可能か、現在 backup 済みかを示します。同期 passkey を許すかは recovery とリスク方針に合わせます。
  • Sign counter: 複製検知の補助信号です。同期 passkey や一部認証器は常に 0、または端末間で単調増加しないため、単独でアカウントを停止しません。
  • Production: challenge の短期サーバ保存・一回限り消費、credential / userHandle の永続化、失敗監査、recovery、複数 credential 管理が必要です。このページのメモリ内 RP は教材用です。

SAML · Kerberos · WebAuthn · mTLS · LDAP · SCIM · DPoP

All implemented from scratch in the Python library. Below is the mental model for each; the code and drills go deeper. implemented

SAML 2.0 implemented

Enterprise SSO's XML predecessor to OIDC. Same shape: SP↔client, IdP↔OP, Assertion↔ID token, Audience↔aud. The hard part is XML-DSig, because you sign a tree, not a byte string — which is where XML Signature Wrapping lives. authlab implements W3C Exclusive XML Canonicalization, including visible namespaces and InclusiveNamespaces PrefixList. Its verifier returns the element that was signed, so a caller cannot be tricked into reading an unsigned sibling.

Source: authlab/saml/ · Drill 09 lands a real XSW attack and shows it refused · optional xmlsec1 interoperability check.

Kerberos implemented

The symmetric-key protocol behind every Active Directory. A KDC issues a TGT (encrypted to krbtgt) and service tickets (encrypted to each service). The service verifies a ticket without ever calling the KDC — that is why it scales. The lab includes working Kerberoasting, AS-REP roasting, golden tickets, and pass-the-ticket, so the AD attack family is concrete.

Source: authlab/kerberos/ · Drill 10.

WebAuthn / passkeys implemented

A key pair per site; the private key never leaves the authenticator, and the signature is bound to the origin. That origin binding is the phishing resistance: a look-alike domain gets no signature because there is no key for it. The lab has a virtual authenticator, a full Python relying party, and a browser-native ceremony that verifies COSE keys, RP ID hash, flags, counters, and assertion signatures.

Source: authlab/webauthn/ · Drill 11 · ブラウザ標準 WebAuthn を開く.

mTLS implemented (real TLS handshake)

Client authentication moved into the TLS handshake itself. This is the one protocol the lab runs over a real socket: a CA we mint issues certs that Python's ssl module genuinely verifies. It also wires into OAuth via RFC 8705 — a token bound to the client certificate (cnf.x5t#S256) is useless without it.

Source: authlab/mtls/, authlab/crypto/x509.py · Drill 12.

DPoP implemented

The software answer to bearer-token theft (RFC 9449). The client holds a key and signs a proof for every request; the token carries the key's thumbprint in cnf.jkt. A stolen token is useless without the private key. Note the deliberate contrast with JWS: here the inline jwk is correct, because it is checked against a thumbprint from a token the AS signed.

Source: authlab/oauth/dpop.py · Drill 07.

LDAP implemented

The directory behind corporate login. Two traps: LDAP injection (build a filter from user input and *)(uid=* matches everyone) and the anonymous-bind trap (a bind with an empty password succeeds as anonymous, so blank-password logins let anyone in). authlab does search-then-bind with a real filter parser and refuses empty passwords.

Source: authlab/directory/ldap.py · Drill 13.

SCIM 2.0 implemented

How identities get provisioned and — crucially — deprovisioned across SaaS apps. The lesson: deactivation (active:false via PATCH), not deletion, is the event that matters, and your app must consult active on every request or ex-employees keep their access until their token expires.

Source: authlab/directory/scim.py · Drill 13.
