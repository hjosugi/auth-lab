🔐 auth-lab

A from-scratch lab for authentication & authorization. Every protocol below is implemented in pure Python (no dependencies) and demonstrated with real cryptography running in your browser via Web Crypto, WebAuthn, and optional WebAssembly Python.

    JWT / JOSE

    JWT は header.payload.signature の3つの base64url をドットで繋いだもの。署名は先頭2セグメントのテキストそのものを覆います。一度中身を見れば、ほとんどの謎は消えます。

    alg=none による偽造

    JWT の古典的攻撃。ボタンを押すと、ペイロードを sub=admin に書き換え、alg=none と空署名を設定して、上のデコーダに読み込みます。

    ライブラリが拒否するもの、その理由

    • alg=none — JWS.verify は既定値のない明示的な許可アルゴリズム一覧を必須にしており、'none' はそこに入りません。
    • RS256→HS256 混同 — 鍵は型付きなので、RSA 公開鍵を HMAC の秘密鍵として渡すことができません。
    • jwk / jku / x5u ヘッダ — 即座に拒否。トークンが自分の検証鍵を指名することは許しません。
    • Claim validation — iss, aud (must contain us), exp, nbf, iat, and OIDC nonce are all checked, not just the signature.
    Source: authlab/jose/jws.py, authlab/jose/jwt.py

    PKCE — Proof Key for Code Exchange

    PKCE は認可コードを「フローを開始した本人」に束縛します。だから盗まれたコードは無価値になります。この10年で最も重要な OAuth の強化策です。

    verifier / challenge のペアを生成する

    verifier はクライアント側に秘密として留まります。ブラウザを通るのはその SHA-256（challenge）だけです。

    code_verifier を challenge と照合する

    トークンエンドポイントがやっていることです。上の verifier を貼り戻す（1文字変えると失敗するのが見えます）。

    なぜ plain は PKCE ではないのか

    plain 方式は verifier そのものをブラウザ経由で送ります — PKCE が「侵害されている前提」に置いている、まさにその経路です。authlab はこれを拒否し S256 を必須にします。さらに、challenge が無いリクエストをサーバが受理するなら攻撃者は単に省略するだけなので、public client では PKCE は任意ではなく必須です。

    パスワードの保存

    パスワードそのものは保存しない。ユーザごとに salt を振る。意図的に遅くする。後からコストを上げられるようパラメータも一緒に保存する。

    パスワードをハッシュする（PBKDF2・本物）

    Python 実装の既定は scrypt（メモリハード）。このブラウザデモが PBKDF2 なのは Web Crypto が公開しているのがそれだからです。原理は同じ — 意図的な遅さ。

    ユーザ列挙を許すタイミングオラクル

    素朴なログインは、存在しないユーザには即座に、存在するユーザには遅く返します。この差が「どのユーザ名が存在するか」を攻撃者に教えてしまいます。

    対策（authlab/passwords/hasher.py の fake_verify）は、存在しないユーザに対してもパスワード誤りと同じ時間を消費します。

    文書、親フォルダ、nested groupを関係タプルだけで辿ります。このengineはauthlab/authz/rebac.pyと同じuserset rewriteを使います。

    Trust binding の negative test

    WebAuthn は challenge だけでは不十分です。RP は type、challenge、origin、rpIdHash、UP/UV flags、署名をすべて検証します。

    本番設計で別途決めること

    • Attestation: none は端末追跡を避けやすい既定。この教材は形式を表示するだけで attestation chain を信頼しません。端末 provenance を要求する管理環境だけ、プライバシーとメタデータ検証を設計して direct を使います。
    • Sync / backup: BE/BS flags は credential が同期可能か、現在 backup 済みかを示します。同期 passkey を許すかは recovery とリスク方針に合わせます。
    • Sign counter: 複製検知の補助信号です。同期 passkey や一部認証器は常に 0、または端末間で単調増加しないため、単独でアカウントを停止しません。
    • Production: challenge の短期サーバ保存・一回限り消費、credential / userHandle の永続化、失敗監査、recovery、複数 credential 管理が必要です。このページのメモリ内 RP は教材用です。

    いずれも Python 実装でゼロから作ってあります。以下は各プロトコルの「頭の中の地図」で、コードとドリルがその先を扱います。実装済み

    SAML 2.0 実装済み

    OIDC の XML 版にあたる、企業 SSO の先行プロトコル。構造は同じで、SP↔クライアント、IdP↔OP、Assertion↔ID トークン、Audience↔aud と対応します。難所は XML-DSig で、署名対象がバイト列ではなく木構造であること — ここに XML 署名ラッピング (XSW) が潜みます。authlab は W3C 排他的正規化（可視名前空間と InclusiveNamespaces PrefixList を含む）を実装し、検証器は署名された要素そのものを返すので、署名のない兄弟要素を読まされることがありません。

    実装: authlab/saml/ · ドリル09 は本物の XSW 攻撃を仕掛けて拒否される様子を見せます · 任意で xmlsec1 との相互運用チェックあり。SAML の解説を読む →

    Kerberos 実装済み

    あらゆる Active Directory の土台にある共通鍵プロトコル。KDC が TGT（krbtgt 鍵で暗号化）とサービスチケット（各サービスの鍵で暗号化）を発行します。サービスは KDC に問い合わせずにチケットを検証できる — これがスケールする理由です。Kerberoasting、AS-REP roasting、ゴールデンチケット、pass-the-ticket が動く形で入っているので、AD 攻撃の系統が具体物として掴めます。

    実装: authlab/kerberos/ · ドリル10。Kerberos の解説を読む →

    WebAuthn / passkeys 実装済み

    サイトごとに鍵ペアを作り、秘密鍵は認証器から出ず、署名はオリジンに束縛されます。このオリジン束縛がフィッシング耐性の本体です — 似せたドメインには対応する鍵が存在しないので、署名がそもそも返りません。仮想認証器、Python の完全なリライングパーティ、そして COSE 鍵・RP ID ハッシュ・フラグ・カウンタ・アサーション署名を検証するブラウザ標準の実演が入っています。

    実装: authlab/webauthn/ · ドリル11 · ブラウザ標準 WebAuthn を開く · WebAuthn の解説を読む →

    mTLS 実装済み（本物の TLS ハンドシェイク）

    クライアント認証を TLS ハンドシェイクの内側に移したもの。このラボで唯一実ソケット上で動くプロトコルです — 自前で発行した CA の証明書を、Python の ssl モジュールが本当に検証します。RFC 8705 で OAuth とも接続していて、クライアント証明書に束縛されたトークン（cnf.x5t#S256）は証明書なしでは無価値になります。

    実装: authlab/mtls/, authlab/crypto/x509.py · ドリル12。mTLS と DPoP の解説を読む →

    DPoP 実装済み

    Bearer トークン窃取に対するソフトウェア側の答え (RFC 9449)。クライアントが鍵を持ち、リクエストごとに proof を署名します。トークンは鍵の thumbprint を cnf.jkt に持ちます。盗まれたトークンは秘密鍵なしでは無価値です。JWS との意図的な対比に注目してください — ここでは inline の jwk は正しいのです。AS が署名したトークン側の thumbprint と照合されるからです。

    実装: authlab/oauth/dpop.py · ドリル07。mTLS と DPoP の解説を読む →

    LDAP 実装済み

    企業ログインの背後にあるディレクトリ。罠は2つ。LDAP インジェクション（ユーザ入力からフィルタを組み立てると *)(uid=* が全員に一致する）と、匿名バインドの罠（空パスワードのバインドは「匿名として成功」するので、空パスワードログインが誰でも通ってしまう）。authlab は本物のフィルタパーサで search-then-bind を行い、空パスワードを拒否します。

    実装: authlab/directory/ldap.py · ドリル13。LDAP と SCIM の解説を読む →

    SCIM 2.0 実装済み

    SaaS 群にまたがってアカウントが作られ、そして——ここが肝心——止められる仕組み。教訓は、重要なイベントは削除ではなく無効化（PATCH による active:false）であること。そしてアプリ側がリクエストごとに active を確認しないと、退職者はトークンが期限切れになるまでアクセスを保持し続けます。

    実装: authlab/directory/scim.py · ドリル13。LDAP と SCIM の解説を読む →

    攻撃

    このラボが防ぐ攻撃の一覧。素朴な実装が破られる様子を見せてから、authlab が拒否する様子を見せます。ここで触れるのは2つ、残りは attacks/catalog.py で実行できます。

    redirect_uri: 完全一致 vs 前方一致

    登録済み: https://app.example.com/callback。攻撃者が使う変種を試してください。
